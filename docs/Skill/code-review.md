# 코드 리뷰 가이드 — 초보 개발자 편

> "리뷰를 잘 하는 것"은 "코드를 잘 짜는 것"만큼 중요한 개발 역량입니다.
> 이 가이드는 리뷰 경험이 없는 팀원도 PR을 보고 의미 있는 피드백을 남길 수 있게 도와줍니다.

---

## 1. 리뷰의 목적

리뷰는 **틀린 걸 잡는 것**이 아니라 **함께 더 좋은 코드를 만드는 것**입니다.

```
[O] "이 부분은 이렇게 하면 더 명확할 것 같아요"
[O] "여기서 이런 경우는 어떻게 되나요?"
[O] "이 접근 좋네요, 저도 배워갑니다"

[X] "이거 왜 이렇게 짰어요?"
[X] "이건 틀렸습니다"
[X] (아무 코멘트 없이 Approve)
```

---

## 2. 리뷰 순서 — 5단계 체크리스트

### Step 1: PR 설명 읽기 (1분)

코드를 보기 전에 PR 설명을 먼저 읽습니다.

```
확인할 것:
□ 무엇을 변경했는지 이해되는가
□ 왜 변경했는지 이유가 있는가
□ 변경 범위가 합리적인가 (한 PR에 한 가지)
```

설명이 부족하면 코드를 보기 전에 먼저 요청:
> "PR 설명에 변경 이유를 추가해주시면 리뷰하기 더 좋을 것 같아요"

### Step 2: 빌드 확인 (2분)

```bash
# PR 브랜치를 로컬에 가져와서 빌드
git fetch origin
git checkout dev/<작성자이름>
make clean && make
```

```
확인할 것:
□ 빌드가 성공하는가 (warning 포함)
□ 기존 테스트가 깨지지 않는가
```

빌드가 안 되면 코드 리뷰 전에 바로 피드백:
> "빌드 시 이런 에러가 나네요: [에러 메시지]. 확인해주세요"

### Step 3: 변경된 파일 목록 훑기 (1분)

GitHub PR의 "Files changed" 탭에서 파일 목록을 먼저 봅니다.

```
확인할 것:
□ 변경된 파일이 PR 설명과 일치하는가
□ 관련 없는 파일이 섞여 있지 않은가
□ 디버그용 printf가 남아있지 않은가
□ .gitignore에 포함되어야 할 파일이 있지 않은가
```

### Step 4: 코드 읽기 (5~15분)

이제 코드를 읽습니다. **작성자가 의도한 순서**대로 읽는 것이 좋습니다.
PR 설명에 "이 파일부터 읽으세요"가 있으면 그 순서를 따릅니다.
없으면 `.h` → `.c` 순서로 (선언 → 구현).

#### 4-1. 로직 확인

```
□ 코드가 PR 설명에 적힌 목적을 달성하는가
□ 빠진 경우(edge case)가 없는가
  - NULL 체크
  - 빈 리스트 처리
  - 0이나 음수 입력
  - 오버플로우
□ 조건문의 논리가 맞는가 (&&, || 혼동)
□ 반복문이 올바르게 종료되는가
□ 리턴값이 의미에 맞는가
```

#### 4-2. 네이밍 확인

```
□ 변수/함수 이름이 역할을 설명하는가
□ 약어가 이해 가능한가 (t → thread? timer? temp?)
□ 컨벤션을 따르는가 (snake_case, UPPER_CASE 등)
```

#### 4-3. 스타일 확인

```
□ 코딩 스타일 가이드를 따르는가
  - PintOS: TAB 인덴트, func () 공백, /* */ 주석
□ 주석이 코드의 "왜"를 설명하는가 (무엇을 하는지는 코드가 말함)
□ 불필요한 주석이 없는가 (주석 처리된 코드 등)
```

#### 4-4. 안전성 확인

```
□ 인터럽트 보호가 필요한 곳에 있는가
□ 동기화 (lock, semaphore)가 올바른가
□ 메모리 할당 후 해제가 짝을 이루는가
□ ASSERT로 전제조건을 검증하는가
```

### Step 5: 피드백 작성 (5분)

확인한 내용을 바탕으로 코멘트를 남깁니다.

---

## 3. 피드백 작성법

### 접두사 규칙

코멘트의 중요도를 접두사로 구분합니다:

| 접두사 | 의미 | 예시 |
|--------|------|------|
| (없음) | 일반 질문/의견 | "이 부분은 왜 이렇게 한 건가요?" |
| `nit:` | 사소한 것 (안 고쳐도 됨) | "nit: 여기 빈 줄 하나 추가하면 좋겠어요" |
| `question:` | 이해가 안 되는 부분 | "question: 이 조건이 false일 때 어떻게 되나요?" |
| `suggestion:` | 개선 제안 | "suggestion: list_insert_ordered를 쓰면 더 효율적일 것 같아요" |
| `bug:` | 버그로 보이는 것 | "bug: 여기서 intr_disable() 없이 sleep_list를 수정하고 있어요" |
| `praise:` | 칭찬 | "praise: 이 비교 함수 깔끔하네요" |

### 좋은 피드백 예시

```
question: 여기서 list_push_back 대신 list_insert_ordered를 쓴 이유가 있나요?
나중에 순서가 보장되어야 하는 상황이 있을 것 같아서 여쭤봐요.
```

```
suggestion: curr->wakeup_tick 대입과 list_insert_ordered 사이에
인터럽트를 끄지 않으면 타이머 인터럽트가 끼어들 수 있을 것 같아요.

이렇게 하면 어떨까요:
old_level = intr_disable ();
curr->wakeup_tick = wakeup_tick;
list_insert_ordered (...);
thread_block ();
intr_set_level (old_level);
```

```
praise: 비교 함수를 별도로 분리한 게 좋네요.
lhs/rhs 네이밍도 명확하고 읽기 편합니다.
```

### 나쁜 피드백 예시

```
[X] "이거 틀렸어요" (뭐가 틀렸는지, 어떻게 고칠지 안 알려줌)
[X] "이상해요" (구체적이지 않음)
[X] "왜 이렇게 짰어요?" (공격적으로 들릴 수 있음)
[X] (아무 코멘트 없이 Approve) (리뷰를 안 한 것과 같음)
```

## 4. Approve / Request Changes 기준

### Approve (승인)

```
[O] 빌드 성공
[O] 로직에 문제 없음
[O] 스타일 큰 문제 없음 (nit만 있음)
[O] 이해 가능한 코드
```

nit 수준의 의견만 있다면 코멘트를 남기되 Approve 합니다.

### Request Changes (수정 요청)

```
[!] 빌드 실패
[!] 버그가 보임
[!] 인터럽트 보호 누락 등 안전성 문제
[!] PR 설명과 코드가 일치하지 않음
```

수정 요청 시 반드시 구체적인 이유와 개선 방향을 함께 제시합니다.

### Comment (의견만)

확신이 없을 때. 질문이나 토론이 필요할 때.
초보자는 Comment로 시작해도 괜찮습니다.

## 5. 리뷰 받는 사람의 자세

### PR 올리기 전 셀프 리뷰

GitHub에서 PR을 만든 직후, "Files changed"를 한 번 읽어봅니다.

```
□ 디버그 printf가 남아있지 않은가
□ 주석 처리된 코드가 있지 않은가
□ 불필요한 파일이 포함되지 않았는가
□ 커밋 메시지가 컨벤션을 따르는가
```

### 피드백에 대한 응답

```
[O] "좋은 지적이에요, 수정하겠습니다" → 수정 후 push
[O] "이런 이유로 이렇게 했어요" → 근거를 설명
[O] "동의합니다. 다만 이번 PR 범위를 벗어나서 다음에 하겠습니다" → 이슈 등록

[X] 피드백 무시
[X] 방어적 태도
```

---

## 6. 리뷰 시간 가이드

| PR 크기 | 파일 수 | 리뷰 시간 | 팁 |
|---------|--------|-----------|-----|
| 소 | 1~3개, ~100줄 | 5~10분 | 바로 리뷰 가능 |
| 중 | 3~5개, ~300줄 | 15~30분 | 하루 안에 리뷰 |
| 대 | 5개+, 300줄+ | 30분+ | PR 쪼개기 요청 |

**PR은 작을수록 좋습니다.** 300줄이 넘으면 작성자에게 쪼개달라고 요청해도 됩니다.

## 7. 리뷰 치트시트

```
┌──────────────────────────────────────────────────┐
│  PR이 왔다! 리뷰 순서                              │
├──────────────────────────────────────────────────┤
│                                                  │
│  1. PR 설명 읽기 (왜, 뭘 바꿨는지)                  │
│                                                  │
│  2. 빌드 확인 (make clean && make)                │
│                                                  │
│  3. 파일 목록 훑기 (관련 없는 파일 없는지)            │
│                                                  │
│  4. 코드 읽기                                     │
│     → 로직 맞는지                                 │
│     → 빠진 경우 없는지                              │
│     → 네이밍/스타일 괜찮은지                         │
│     → 안전한지 (인터럽트, 동기화, NULL)               │
│                                                  │
│  5. 피드백 작성                                    │
│     → 접두사 사용 (nit/question/suggestion/bug)    │
│     → 칭찬도 남기기                                │
│     → Approve / Request Changes / Comment         │
│                                                  │
└──────────────────────────────────────────────────┘
```
