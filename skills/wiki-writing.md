# WIKI 문서 작성 스킬

이 스킬은 Jungle-12-303/WIKI 레포에 학습 내용을 작성할 때 따라야 할 문법, 구조, 품질 기준을 정의합니다. 외부 소스(개인 학습 노트, CSAPP 정리, 대화 기록 등)에서 WIKI로 내용을 옮기거나, 새로 키워드를 작성할 때 이 스킬을 따릅니다.

---

## 1. 문서 구조

모든 키워드 파일은 아래 구조를 따릅니다.

```markdown
---
title: <키워드 제목>
category: <L0 카테고리명>
keyword: <상위 키워드 (하위 레벨인 경우)>
tags: [태그1, 태그2, ...]
summary: <한 문장 요약>
---

# <키워드 제목>

> <한 줄 요약 — 이 키워드가 무엇인지 한 문장으로>

## 개요

이 키워드가 왜 중요한지, 어떤 맥락에서 등장하는지 2-3문장.

## 상세 설명

본문. 소제목(###)으로 구분.

## 참고 자료

- [출처 이름](URL)
```

**프런트매터 필드 설명:**

| 필드 | 필수 | 설명 |
|------|------|------|
| `title` | O | 문서 제목 (한국어) |
| `category` | O | L0 카테고리명 (`OS`, `네트워크`, `Malloc lab` 등) |
| `keyword` | 하위 레벨만 | 상위 키워드명 (예: `가상 메모리` 아래의 `fork와 Copy on Write`) |
| `tags` | O | 검색용 영문 태그 배열 |
| `summary` | O | 한 문장 요약 (50자 내외 권장) |

---

## 2. 본문 작성 규칙

### 서술 순서

1. **개요** — 이 키워드가 왜 존재하는지, 어떤 문제를 푸는지
2. **상세 설명** — 원리, 구조, 동작 방식
3. **(선택) 코드 예시** — 이해를 돕는 최소한의 코드
4. **(선택) 비교 표** — 유사 개념과의 차이
5. **(선택) 관련 키워드** — WIKI 내 다른 문서 링크
6. **참고 자료** — 출처 URL

### 문체

- 경어체가 아닌 **평서체**(합니다/입니다가 아닌 ~한다/~이다)를 기본으로 합니다. 단, 팀 내 합의가 있으면 경어체도 허용합니다.
- 한 문단은 3-5문장을 기준으로 합니다. 한 문장짜리 문단은 가급적 피합니다.
- 코드 블록에는 반드시 언어 태그를 붙입니다 (```c, ```python, ```text 등).
- mermaid 다이어그램은 허용하지만, ASCII 다이어그램도 동등하게 유효합니다.

### 금지 패턴

| 금지 | 이유 | 대안 |
|------|------|------|
| `_작성 필요_`를 남긴 채 커밋 | 빈 섹션은 다른 사람에게 혼란 | 내용을 채우거나 섹션 삭제 |
| 외부 이미지 직접 링크 | 링크 깨짐 위험 | 텍스트/코드/다이어그램으로 대체 |
| 본인만 아는 약어 | 다른 사람이 못 읽음 | 첫 등장 시 풀네임 병기 |
| 교재 본문 그대로 복사 | 저작권 문제 | 자기 말로 재구성 |
| 한 파일에 여러 키워드 혼합 | 검색/관리 어려움 | 키워드당 파일 하나 |

## 3. 외부 소스에서 WIKI로 옮기는 절차

개인 학습 노트, CSAPP 정리, 대화 기록 등 외부 소스를 WIKI에 반영할 때 아래 절차를 따릅니다.

### 3-1. 대상 식별

외부 소스의 각 문서(또는 섹션)에 대해 다음을 판단합니다:

| 판단 항목 | 질문 |
|-----------|------|
| WIKI 대응 키워드 존재 여부 | 이 내용에 해당하는 WIKI 키워드 파일이 이미 있는가? |
| WIKI 키워드 상태 | 있다면 `작성 필요`/`작성 중`/`완료` 중 무엇인가? |
| 내용 수준 비교 | 외부 소스가 WIKI보다 더 상세하거나, 다른 관점을 가지는가? |
| 키워드 분류 | WIKI의 어느 카테고리(L0), 어느 깊이(L1~L9)에 들어가는가? |

### 3-2. 행동 결정

| WIKI 키워드 상태 | 외부 소스 수준 | 행동 |
|------------------|----------------|------|
| `작성 필요` (빈 템플릿) | 충분한 내용 있음 | 외부 소스를 WIKI 문법으로 **변환하여 채움** |
| `작성 필요` | 내용 부족 | 스킵 또는 개요만 작성 후 `작성 중` 표기 |
| `작성 중` (다른 사람) | - | **절대 덮어쓰지 않음**. 담당자와 논의 |
| `완료` | 외부 소스가 더 나음 | WIKI 기존 내용과 **병합**. 더 나은 설명을 선택 |
| `완료` | 외부 소스가 동등/미달 | **스킵**. 억지로 추가하지 않음 |
| 키워드 자체가 없음 | 독립 키워드 가치 있음 | 새 키워드 파일 **생성** |
| 키워드 자체가 없음 | 기존 키워드 하위 | 하위 레벨 폴더 **분리** 검토 |

### 3-3. 병합 원칙

두 소스(WIKI 기존 + 외부)를 합칠 때:

1. **더 명확한 설명을 선택한다.** 길이가 아니라 이해하기 쉬운 쪽을 택한다.
2. **코드 예시는 하나만 남긴다.** 같은 개념을 보여주는 코드가 여러 개 있으면 가장 간결한 것 하나를 선택한다.
3. **다이어그램은 보충 관계일 때만 둘 다 유지한다.** 같은 것을 보여주는 다이어그램이 두 개면 하나를 삭제한다.
4. **출처를 남긴다.** 외부 소스의 원본 위치를 `참고 자료` 섹션에 추가한다.

### 3-4. 프런트매터 변환

외부 소스에 YAML 프런트매터가 있더라도, WIKI 형식으로 재작성합니다.

외부 소스 프런트매터 예시:
```yaml
title: 가상 메모리가 푸는 세 가지 문제
category: OS
keyword: 가상 메모리
tags: [virtual-memory, page-table, protection]
summary: 가상 메모리는 캐싱, 관리, 보호 세 가지 문제를 하나의 번역 테이블로 풀어냅니다.
source: _krafton/SW_AI-W07-SQL/docs/blog/concepts/03-virtual-memory-three-problems.md
```

WIKI 변환 후:
```yaml
title: 가상 메모리가 푸는 세 가지 문제
category: OS
keyword: 가상 메모리
tags: [virtual-memory, page-table, protection]
summary: 가상 메모리는 캐싱, 관리, 보호 세 가지 문제를 하나의 번역 테이블로 풀어냅니다.
```

`source` 필드는 WIKI에서는 사용하지 않습니다. 출처는 `참고 자료` 섹션에 기입합니다.

## 4. 중복 방지 규칙

### 4-1. 추가 전 반드시 확인

새 내용을 추가하기 전에 다음을 확인합니다:

1. **같은 키워드 파일이 이미 있는가?** → `docs/` 하위를 검색
2. **비슷한 키워드가 다른 카테고리에 있는가?** → 예: `os/paging.md`와 `pintos/project3-vm/paging.md`
3. **기존 키워드의 하위 섹션으로 이미 다뤄졌는가?** → 예: `virtual-memory.md` 안에 COW 설명이 한 단락 있을 수 있음

### 4-2. 중복 유형별 처리

| 중복 유형 | 예시 | 처리 |
|-----------|------|------|
| 완전 중복 | 같은 개념을 같은 깊이로 설명 | 더 나은 쪽을 남기고 하나 삭제 |
| 깊이 차이 | OS 개념 vs Pintos 구현 | 둘 다 유지. 관련 키워드 링크로 연결 |
| 관점 차이 | 이론 vs 실습 경험 | 둘 다 유지. 각자의 카테고리에 배치 |
| 부분 중복 | A 파일의 한 섹션이 B 파일 전체와 겹침 | A에서 해당 섹션을 요약으로 줄이고 B로 링크 |

### 4-3. 양 때문에 억지로 추가하지 않는다

다음 경우에는 WIKI에 추가하지 않습니다:

- 기존 `완료` 키워드가 이미 충분히 상세하고, 추가할 새로운 관점이 없는 경우
- 외부 소스의 내용이 기존 키워드의 한 문단 이하 분량인 경우 (기존 파일에 보충)
- 개인 메모 수준으로, 다른 사람이 읽어도 학습에 도움이 되지 않는 경우

**핵심 원칙: "이 내용이 없으면 다른 사람이 이 키워드를 이해하는 데 빈틈이 생기는가?" 에 '아니오'면 추가하지 않는다.**

## 5. 하위 레벨 분리 기준

기존 키워드 파일이 아래 조건 중 하나를 만족하면 하위 폴더로 분리합니다:

1. 파일이 300줄을 넘는 경우
2. `##` 소제목이 5개 이상이고, 각 소제목의 내용이 독립적으로 읽힐 수 있는 경우
3. 외부 소스에서 같은 키워드의 하위 개념이 3개 이상 추가되는 경우

분리 절차는 CONTRIBUTING.md 9절을 따릅니다.

## 6. 체크리스트

키워드를 작성하거나 외부 소스를 반영한 뒤, 커밋 전에 확인합니다:

- [ ] 프런트매터 필수 필드 (`title`, `category`, `tags`, `summary`) 가 모두 채워져 있다
- [ ] `_작성 필요_`나 `_링크 추가_` 같은 플레이스홀더가 남아 있지 않다
- [ ] 코드 블록에 언어 태그가 있다
- [ ] 해당 카테고리 README.md의 상태가 업데이트되었다
- [ ] 같은 내용을 다루는 기존 키워드가 없는지 확인했다
- [ ] 기존 `완료` 키워드에 새 내용을 억지로 덧붙이지 않았다
- [ ] 교재 본문을 그대로 복사하지 않고 자기 말로 재구성했다
- [ ] 관련 키워드가 있으면 상호 링크를 걸었다
